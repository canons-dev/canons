## Agent 协作约定（canons）

适用于本仓库所有 coding agent。每条写要达到的结果和理由；提到的做法只是例子，可以换更好的，结果不能打折。区块外的项目规则在此基础上补充，可以收紧 C1、C3、C8、C9、C11、C12、C20，但不能放宽。

### 真源与加载

- **C1** 每份约定只有一个可编辑的真源，各客户端读到的才是同一份：`AGENTS.md`、`.agents/rules/`、`.agents/skills/`。客户端入口是薄适配：`CLAUDE.md` 只有一行导入 `@AGENTS.md`，`.claude/rules`、`.claude/skills` 是相对软链接；复制或反向链接都会漂移。
- **C2** 约束放在与生效范围对应的层级：红线放本文件，子系统约束放带 `paths` frontmatter 的规则，多步流程做成技能。红线不下放，下层不保证被加载。
- **C3** 动手前知道哪些规则约束要改的文件，收尾时实际 diff 满足它们。客户端原生加载规则不完整，以 `npx canons scopes <路径>...`（新文件传拟创建的路径）和 `npx canons scopes --changed` 为准。没有命中时本文件照样适用。它提示 canons 有新版本时，先完成当前任务再问用户：同意就按 `canons` 技能升级，拒绝就运行 `npx canons latest --decline <版本>`。
- **C4** 本文件要被每个客户端完整加载，所以不超字节预算（`npx canons verify` 检查）。腾空间靠精简措辞或把理由移进文档，绝不删红线。

### 知识与文档

- **C5** 要 agent 记住的约定写进仓库文件并经 git review，不只存在客户端私有 memory。跨模块的共性踩坑集中在一个 lessons 文件（现象、根因、避法、不变量），同主题合并。
- **C6** 文档和规则只写当前知识及理由，不写历史。代码里看得到的只留指针，不变量用测试守护，同一约束只写一处，同一概念只用一个词。agent 自己能推断的不写（空泛建议、复述 linter 规则）。不允许例外的规则做成确定性检查（测试、CI、hook），不靠加重语气；某条规则总被忽略时，精简文件或加检查，而不是加强调。
- **C7** 临时文件、一次性脚本和在途方案放临时目录（C17 没另定时为 `tmp/`，git 忽略）；可复用工具入库。长期内容不指向临时目录。

### 协作与授权

- **C8** Git 状态变化（commit、push、pull、merge、rebase、reset、stash、tag、切分支、建 PR）由用户决定，因为它牵动共享历史、他人工作和发布。只在用户明确指令下做；只读命令和 C9 的同步上游除外，已授权任务所需的步骤不必重复确认。
- **C9** 从上游最新代码开始，且不覆盖他人在途修改：先看清工作区，再同步（例如 fetch 后快进，或从刚拉取的基线开分支）。同步需要合并、变基或会动到他人改动时，或要改另一个 session 正在改的文件时，先问。worktree 不隔离数据库、端口等共享资源。
- **C10** 需求、行为、接口或命名有实质歧义，或用户的决定与本约定冲突时，由用户拍板：指出分歧，给出互斥选项和你的推荐及代价，然后等待。
- **C11** 事实与推测分开：未验证的判断标明依据和验证方法；二手结论注明来源，不升格为事实。
- **C12** 缺少某种能力（子 agent、浏览器、提问界面）只改变做法，不改变要求：必需的确认和验证照做，没能验证的如实说明。
- **C13** 交接后接手方不用回头问就能继续：在 `tmp/` 写下目标、范围、改动文件、设计决定、验证结果、剩余工作和待决项，并显式交给对方。长期知识回写文档。
- **C14** 每个阶段收尾（包括非交互运行）都给出明确的结清判定，让用户不用回看就知道本 session 是否做完、能否归档；每个未结项写明卡点、负责方和下一步（例如用表格）。未提交的改动、未同步的上游、PR 未合、待部署、待复测、待用户决定都算未结。

### 完成改动

- **C15** 改动要证明能用才算完成：开工前先定好用什么检查来证明（例如先写一个能复现 bug 的失败测试；多步任务每步都有检查），收尾前跑过。`AGENTS.md` 在本区块外记下确切的构建、测试、lint 命令和单跑一个测试的方法，让每个 agent 用同样的方式验证。改动落地时代码、测试、文档和规则一致：可测试的逻辑有测试，受影响的文档和规则在同一次改动里同步。汇报同步了什么，没同步的说明原因。

### 语言与目录

- **C16** `AGENTS.md` 在本区块外记下 UI 语言（所有面向用户的文字：按钮、标签、占位符、空状态、错误、示例、默认值、通知）和开发语言。没记 UI 语言时，写这类文字前先和开发者确认并记下。与开发者交流、写 commit、PR、文档和注释用开发语言，没记时用系统语言；标识符、路径、命令和技术名词保持原样。
- **C17** 东西放在人和 agent 预期的地方：按 `AGENTS.md` 记下的目录结构，没记时源码放 `src/`、文档放 `doc/`、临时文件放 `tmp/`（git 忽略），其他顶层目录也用三个字母（如 `out/`、`ops/`、`bin/`）。根目录只放仓库级配置和 `README.md`、`AGENTS.md` 这类入口。

### 在代码库里工作

- **C18** 新名字和邻居成套：先长度一致（字母数，不含扩展名），再对齐词性、单复数、分段、大小写和分隔符。邻居不一致时跟数量更多、更新的一组；拿不准就问。
- **C19** 改共享语义（API 参数、hook、常量）后所有调用方仍然正确，所以先 review 全部调用点。产生必须多处同步的耦合时，作为同步点记进文档。
- **C20** 其他仓库（兄弟仓库、参考实现、附近的依赖源码）只读，用户许可后才改。在 worktree 里先确认兄弟仓库的实际路径，不假定是 `../`。
- **C21** 项目有意推迟或不做的能力列在文档里，由项目决定；不顺手补上。看起来缺了什么，先查这份清单。
- **C22** 只做用户要的事，范围以用户说的为准，不把指令读得比原意更宽。每一行改动都能对应到需求：不顺手重排或重构，沿用周边风格；自己改动造成的无用代码删掉，原本就有的死代码只提一句。说出所依据的假设，有更简单的做法就说出来；不为只用一次的代码做抽象，不加没人要的配置，不处理不可能发生的错误。一次性的要求不是要记下来的长期规则，一个决定也不需要加防止它被反转的守护。额外的功能、规则、文档或防护等用户要了再做，最多一句话提出。改动本身要求的同步（C15、C19）不算额外。
