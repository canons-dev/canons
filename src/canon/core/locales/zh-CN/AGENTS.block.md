## Agent 协作约定（canons）

本区块适用于在本仓库工作的所有 coding agent（Codex、Claude Code、Cursor、Copilot 等）。每条先写要达到的结果及理由；写到的具体做法只是参考，有更好的做法可以换，但结果和判据不打折。区块外的项目规则在此基础上补充；项目规则可以收紧 C1、C3、C8、C9、C11、C12、C20，但不能放宽。

### 真源与加载

- **C1** 每份约定只有一个可编辑的真源，所以每个客户端读到的都是同一份：`AGENTS.md`、规则目录（`.agents/rules/`）和技能目录（`.agents/skills/`）。`CLAUDE.md`、`.claude/rules`、`.claude/skills` 等客户端入口都是指向真源的相对软链接；复制出第二份或反向链接都会让两边漂移。
- **C2** 约束放在它生效范围对应的层级，需要时一定读得到，不需要时不占上下文：全局红线放本根文件，子系统约束放规则目录并用 `paths` frontmatter 声明范围，多步流程做成按需加载的技能。红线不得下放，因为下层不保证被加载。
- **C3** 动手前要知道哪些规则约束你要改的文件，收尾时实际 diff 涉及的规则都要满足。客户端原生加载规则并不完整，以 `npx canons scopes <文件或目录>...`（新文件传拟创建路径）和 `npx canons scopes --changed` 的输出为准。没有命中不等于没有约束：本文件始终适用。
- **C4** 本文件要被每个客户端完整加载，所以保持在字节预算内（`npx canons verify` 会检查）。腾空间时精简措辞或把理由移进文档，绝不删红线。

### 知识与文档

- **C5** 要求 agent 记住的约定，所有人和 agent 都要看得到、能 review：写进仓库文件并经 git review，不能只存在某个客户端的私有 memory 里。跨模块的共性踩坑集中写进一个 lessons 文件（现象、根因、怎么避开、不变量），同主题合并，让下一个人一次查到。
- **C6** 文档和规则给读者当前正确的知识和理由：不写历史；能从代码直接看到的事实只留指针，免得复述后漂移；必须守住的不变量用测试守护，不只靠文字；同一约束只写在一处。
- **C7** 仓库里只留长期有用的东西。临时文件、一次性脚本和在途方案放临时目录（C17 没有另行约定时为 `tmp/`，git 忽略）；可复用的工具必须入库。文档和代码不得指向临时目录里的文件，它们随时会消失。

### 协作与授权

- **C8** Git 状态的变化（commit、push、pull、merge、rebase、reset、stash、tag、切分支、建 PR）由用户决定，因为它影响共享历史、别人的工作和发布。没有用户明确指令就不做；只读命令和 C9 所述的同步上游不受此限；已授权任务所需的步骤不必重复确认。
- **C9** 你的改动基于上游最新代码，并且不覆盖他人的在途修改，免得在旧代码上返工或制造冲突：动手前弄清工作区已有哪些改动（例如 `git status`），并拉取上游最新代码（例如 `git fetch` 后快进当前分支，或从刚拉取的基线新开分支）。同步需要合并、变基或会动到别人的在途修改时，先问用户；要改另一个 session 正在改的文件，先确认。并行工作优先用独立 worktree；worktree 不隔离数据库、端口等共享资源。
- **C10** 需求、行为、接口或命名有实质歧义，或用户的决定与本约定冲突时，由用户拍板，不要自行假设。让用户能快速、知情地决定：指出分歧点，给出互斥选项和你的推荐及其代价（例如 2–4 个选项、推荐项放第一个），然后等待决定。
- **C11** 读者要分得清事实和推测：未验证的判断标注为未验证，并写明依据和验证方法；二手结论注明来源，不得升格为事实。
- **C12** 缺少某种能力（没有子 agent、没有浏览器、没有提问界面）只改变做法，不改变要求：必需的确认和验证照样要做到，做不到的如实说明。
- **C13** 交接后，接手的 agent 不用回头问就能继续。交接记录放在 `tmp/` 并显式交给对方，通常要覆盖目标、范围、改动文件、设计决定、验证结果、剩余工作和待决项。长期知识回写到文档。
- **C14** 每个阶段收尾时，用户要能一眼看出本 session 是否做完、能否归档；没做完的，每一项卡在哪、归谁、下一步做什么都要清楚（例如用表格：事项 | 状态或卡点 | 负责方 | 下一步）。PR 未合、待部署、待复测、待用户决定都算没做完。

### 完成改动

- **C15** 改动落地时，代码、测试、文档和规则说的是同一件事：能自动测试的逻辑有测试，受影响的文档和不变量所在的规则在同一次改动里同步。汇报同步了什么；没同步的说明原因。

### 语言与目录

- **C16** 用户看到的文字用项目的 UI 语言，开发者读的内容用开发语言，两者都记在 `AGENTS.md` 本区块之外。UI 语言覆盖所有面向用户的文字：按钮、标签、占位符、空状态、错误、示例、默认值和通知；没有记下时，写这类文字之前先和开发者确认并记下来，不要猜。与开发者交流，以及写 commit 信息、PR 描述、文档和代码注释，用记下的开发语言；没有记下时用系统语言。标识符、路径、命令和技术名词保持原样。
- **C17** 东西放在哪要能被人和 agent 预测到，以 `AGENTS.md` 里记下的目录结构为准。没有记下时默认：源码放 `src/`，文档放 `doc/`，临时文件放 `tmp/`（git 忽略），其他顶层目录也用三个字母的名字（例如 `out/`、`ops/`、`bin/`）。根目录只放仓库级配置和 `README.md`、`AGENTS.md` 这类入口文件。

### 在代码库里工作

- **C18** 新文件和新目录的名字要和邻居看起来是同一套：首先长度一致（名字的字母数相同，不含扩展名），然后词性、单复数、分段、大小写和分隔符一致。邻居之间不一致时，跟数量更多、更新的那一组；确实拿不准时询问。
- **C19** 改了共享语义（API 参数、hook、常量等）之后，所有调用方和使用点仍然正确，所以动手前 review 全部调用点。改动产生了必须在多处保持一致的耦合时，把它作为同步点记进文档，让下一个人知道要一起改。
- **C20** 是否修改其他仓库（兄弟仓库、参考实现、放在附近的依赖源码）由用户决定：可以读，未经许可不改。在 worktree 里 `../` 不一定是兄弟仓库，先确认实际路径。
- **C21** 有意推迟或不做哪些能力由项目决定，清单写在文档里；看起来再有用也不顺手补上。看起来缺了什么时，先查这份清单。
